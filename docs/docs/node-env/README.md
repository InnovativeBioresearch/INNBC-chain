# INNBC Node Environment Reference

This page documents the node env files generated by `innbc-chain node create` and `innbc-chain node prepare`, and the runtime settings used by systemd-managed validator nodes.

<!-- START ALPHA CHANGE 2284 -- distinguish service environments from direct command defaults -->
Production node services read `/etc/innbc/<node>.env`; direct foreground commands do not automatically read that file.

The updated service passes the nine `INNBC_JSONRPC_*` admission settings shown in the examples below to their corresponding `--json-rpc-*` flags. Newly generated node environments include them. Preserved older environments inherit the same defaults from the service when the settings are absent.

All admission values must be positive, and `INNBC_JSONRPC_MAX_EXPENSIVE` must not exceed `INNBC_JSONRPC_MAX_CONCURRENT`. Editing an env file affects the next node start, not the running process.

Local foreground commands inherit the same defaults from Go unless explicit CLI flags override them. The local admission tables near the end of this guide list those flags.
<!-- FINISH ALPHA CHANGE 2284 -- distinguish service environments from direct command defaults -->

## Env File Ownership

Each node has one env file:

```text
/etc/innbc/node1.env
/etc/innbc/node2.env
/etc/innbc/node3.env
/etc/innbc/node4.env
/etc/innbc/node5.env
/etc/innbc/node6.env
```

The production installer does not create or overwrite these real env files. It only installs the binary, genesis, systemd service, and example config files.

Real node env files are created by:

```bash
sudo innbc-chain node create
sudo innbc-chain node prepare
```

<!-- START ALPHA CHANGE 1933 -- document mandatory per-node service configuration -->
The production systemd template requires the environment file corresponding to the service instance:

```text
innbc-node@node1 → /etc/innbc/node1.env
innbc-node@node2 → /etc/innbc/node2.env
innbc-node@nodeN → /etc/innbc/nodeN.env
```

The file is not optional. If it is missing or cannot be read, systemd fails the service before starting the INNBC binary. Node-specific ports, history mode, snapshot source, and storage configuration therefore cannot silently fall back to the template’s node1-oriented defaults.

`node start all` discovers configured nodes from the existing `/etc/innbc/node*.env` files. Starting a named service directly is also safe because the systemd unit independently requires that named node’s environment file.
<!-- FINISH ALPHA CHANGE 1933 -- document mandatory per-node service configuration -->

Existing environment files are never overwritten.

## Identity Batch Size and Node Numbering

`node create` accepts up to ten new identities per invocation. Automatic allocation and `node info` support node1 through node100, independently of the selected node mode.

These are separate limits:

| Limit | Value |
| --- | --- |
| New identities per `node create` invocation | 1–10 |
| Supported automatic node numbers | 1–100 |

Creation selects available numbers in ascending order and fills gaps.

A number is reserved when either its node path or its environment path exists. Directories, ordinary files and symlinks, including dangling symlinks, all reserve the corresponding number.

With no gaps or conflicting files:

```text
node create 10 → node1–node10
node create 10 → node11–node20
node create 11 → rejected
```

The complete requested allocation is checked before parent directories or identities are created. Insufficient capacity rejects the invocation without creating anything.

Creation then exclusively reserves each node directory and environment file before generating its keys. If a destination appears after planning, creation fails rather than overwriting it or reusing an existing identity directory.

Capacity rejection and later execution failure have different guarantees. A later filesystem or key-generation failure can leave previously completed nodes and a partial current slot. Existing identities are preserved; there is no automatic batch rollback. A later invocation treats any remaining node or environment path as reserved.

Deleting only an environment file does not make an existing identity directory available for `node create`.

The generated port assignments remain:

| Service | Formula | node1–node100 |
| --- | --- | --- |
| JSON-RPC | `8544 + nodeNumber` | 8545–8644 |
| Operator gRPC | `9631 + nodeNumber` | 9632–9731 |
| Libp2p | `30300 + nodeNumber` | 30301–30400 |

The generated ranges do not overlap. Other applications or manually configured addresses can still cause port conflicts.

This numbering policy does not imply that one host has sufficient resources to run 100 nodes.

`node prepare` retains its existing deterministic behavior: a count of six targets node1–node6, rather than the next available six numbers. Its count remains limited to 1–10.

Node1 continues to default to full history. Subsequent automatically numbered nodes default to recent history.

## Read-Only Node Inspection

<!-- START ALPHA CHANGE 3368 -- explain post-creation validation and its deliberate read-only scope -->

### Why Inspection Is Separate From Creation

The earlier numbering defect allowed creation to advance beyond the node numbers accepted by inspection. Creation now limits each invocation to ten new identities while supporting automatically numbered node1–node100. It plans the complete requested allocation before writing and refuses occupied identity or environment destinations.

A separate limitation remains intentional: creation is not an atomic batch transaction. A filesystem or key-generation failure can leave completed nodes and an incomplete current slot.

The supported response is read-only inspection of the files that remain. Inspection does not roll back a batch, delete a partial slot, regenerate keys or modify an environment file. Rerunning `node create` does not repair an occupied partial slot; allocation treats that slot as reserved.

After creation, after importing existing keys, or after a failed provisioning attempt, inspect the selected installation before registration or startup:

```bash
sudo innbc-chain node info all \
  --base-dir /var/lib/innbc \
  --config-dir /etc/innbc
```

For a local workspace, run from the repository root:

```bash
./localtestclient/bin/innbc-chain node info all \
  --base-dir localtestclient/nodes \
  --config-dir localtestclient/config
```

Use an account that can read the identity and environment files. Inspection does not change their permissions to obtain access.

### What Is Checked

| Area | Inspection behavior |
| --- | --- |
| Identity layout | Requires the canonical identity directories and all three key files. |
| ECDSA key | Checks hexadecimal encoding, exact length and the valid nonzero scalar range, then derives the operator address. |
| BLS key | Checks the supported encoding and valid nonzero scalar range, then generates and verifies the operator-bound public possession proof. |
| Libp2p key | Decodes the key and verifies a local signing challenge; secp256k1 keys also receive scalar checks. |
| File inputs | Requires regular key and environment files and bounds reads to 4 KiB per key and 64 KiB per environment file. |
| Environment | Parses stored assignments without executing them; checks required entries, duplicate recognized settings, the selected data directory, address ports, optional history mode and optional peer-directory URL. |
| Reporting | Reports identity and environment status separately and continues inspecting later discovered slots after a node-level validation failure. |

`Environment status|valid` means that the implemented inspection checks passed. It does not mean that every displayed numeric setting, referenced genesis or snapshot, filesystem ownership, network endpoint or runtime prerequisite has been validated.

Discovery does not remember an earlier creation request. If only node1 and node2 remain, inspection does not infer that node3 was intended. If node1–node3 and node5 exist, the interior node4 gap is reported. An empty discovery result is not proof that a previous creation request completed.

<!-- FINISH ALPHA CHANGE 3368 -- explain post-creation validation and its deliberate read-only scope -->

Inspect one node:

```bash
innbc-chain node info node2 \
  --base-dir /var/lib/innbc \
  --config-dir /etc/innbc
```

Inspect all discovered node slots:

```bash
innbc-chain node info all \
  --base-dir /var/lib/innbc \
  --config-dir /etc/innbc
```

Add `--json` for structured output.

Inspection reads canonical key files directly. It does not initialize storage, create directories, change permissions, repair files or regenerate identities.

Private keys are read locally to validate their encoding and cryptographic usability and derive the public identity. Only the operator address, BLS public key, operator-bound BLS proof, peer ID and public configuration are reported. Private-key contents and decoder input are never deliberately included in diagnostics.

Key and environment inspection require regular files. Symlinks and other non-regular files are reported as invalid inspection inputs.

### Discovered Slots and Missing Identities

`node info all` considers both node paths and environment paths within node1–node100. It inspects slots from node1 through the highest discovered number.

If node1–node3 and node5–node10 exist, the report includes:

```text
WARNING: NODE 4 IDENTITY MISSING
```

If only node1 and node2 exist, no node3 entry is printed.

Completely unoccupied gaps produce warnings without making the command fail. An environment-only slot is incomplete and reports its missing identity.

### Independent Environment Inspection

Environment inspection continues even when identity validation fails.

A valid identity without its environment still produces public identity information and:

```text
WARNING: NODE 2 ENVIRONMENT MISSING
```

The report includes only recognized public environment settings. Unknown settings are omitted. Peer-directory URL user information, query parameters and fragments are removed from displayed values.

Environment files are parsed as stored assignments; they are never executed or sourced. Basic checks cover required settings, the selected node's data directory, address ports, history mode and the peer-directory URL.

This is an inspection of stored configuration, not a reconstruction of systemd's complete environment interpretation or proof of a running service's effective settings.

Registration multiaddr templates retain the generated default port formulas. Actual stored listen addresses are reported separately in the environment settings.

### Exit Status and Validation Scope

A complete valid selection returns status 0. An empty installation also returns status 0 with an empty-discovery report.

An occupied slot with missing or invalid identity data or environment data produces status 1 after all selected slots have been reported. JSON mode retains the detailed report on standard output and the terminal error object on standard error.

Inspection can establish that keys are valid and usable. Detecting replacement with another valid identity requires comparison against a trusted expected identity.

## Private and External Validator Profiles

Both `node create` and `node prepare` accept `--mode private-local` and `--mode external-validator`.

Use `private-local`, the default, for local testing and private deployments. Use `external-validator` for externally reachable production validators contacting the centralized public peer directory.

These modes select initial environment values. Both use the same node runtime, and operators can customize either generated env file before starting the service.

For node1, the generated networking defaults are:

| Setting | `private-local` | `external-validator` |
| --- | --- | --- |
| `INNBC_LIBP2P_ADDR` | `127.0.0.1:30301` | `0.0.0.0:30301` |
| `INNBC_NAT_ADDR` | Empty | Empty |
| `INNBC_DNS_ADDR` | Empty | Empty |
| `INNBC_PEER_DIRECTORY_ENABLED` | `true` | `true` |
| `INNBC_PEER_DIRECTORY_URL` | `http://127.0.0.1:8080/api/v1/peers/exchange` | `https://innbcchain.io/api/v1/peers/exchange` |
| `INNBC_JSONRPC_ADDR` | `127.0.0.1:8545` | `127.0.0.1:8545` |
| `INNBC_GRPC_ADDR` | `127.0.0.1:9632` | `127.0.0.1:9632` |

Additional nodes receive incremented default ports. The networking profile does not select the history role: node1 defaults to full history, while subsequent nodes default to recent history.

### Listening and Advertised Addresses

`INNBC_LIBP2P_ADDR` controls where the node listens. `INNBC_NAT_ADDR` and `INNBC_DNS_ADDR` control the address advertised to other peers.

Both profiles include these operator-editable placeholders:

```ini
INNBC_NAT_ADDR=
INNBC_DNS_ADDR=
```

For public networking, configure the reachable advertised address appropriate to the deployment:

- `INNBC_NAT_ADDR`: public IPv4 address only, without a scheme or port.
- `INNBC_DNS_ADDR`: DNS multiaddress prefix, such as `/dns4/validator.example.com`, without a TCP port or peer ID.

Choose one advertised-address setting. When both are populated, NAT takes precedence. Both use the port configured in `INNBC_LIBP2P_ADDR`; an independent advertised port is not currently supported.

For direct exposure, bind the node to a reachable interface and provide any required router or firewall forwarding.

For a same-server TCP proxy, the backend can remain on loopback while advertising the gateway. For example:

```ini
INNBC_LIBP2P_ADDR=127.0.0.1:30301
INNBC_NAT_ADDR=160.153.178.230
INNBC_DNS_ADDR=
INNBC_PEER_DIRECTORY_ENABLED=true
INNBC_PEER_DIRECTORY_URL=https://innbcchain.io/api/v1/peers/exchange
```

This example requires separate TCP forwarding from `160.153.178.230:30301` to `127.0.0.1:30301`. The NAT setting advertises the endpoint; it does not create forwarding. Nodes on the same server must also be able to reach the advertised gateway endpoints.

The peer-directory HTTP endpoint distributes addresses; P2P traffic connects separately to the advertised TCP endpoints. A publicly proxied directory can retain its private backend listener.

### Applying Configuration Changes

Editing an env file can convert a private profile into an externally reachable configuration without regenerating keys. Restart the node to apply changed settings.

The node submits its advertised multiaddress in a signed directory exchange. A successful authorized exchange replaces the stored address for the same peer ID. Other running nodes learn the updated address through the normal manual directory-refresh workflow.

Selecting `external-validator` does not install a proxy or grant validator authorization. Those remain separate deployment and registration steps.

For explicitly accelerated rotation testing, replace the history flags with:

```bash

```

This optional configuration opens a new segment approximately every minute at a two-second block interval. Once its retention window fills, it retains between 1,051 and 1,080 blocks. Segment retirement begins only when the retained segment count is exceeded.

These are optional testing overrides, not the default local configuration or the absolute minimum accepted by the software.

The EVM requires access to hashes from the preceding 256 blocks. This applies during validator execution even when application RPC uses only a full-history node. JSON-RPC block-range and fee-history limits do not change that execution requirement.

<!-- START ALPHA CHANGE 2216 -- explain an example of insufficient execution ancestry -->
Avoid settings such as retention 120 blocks with 30-block segments for general contract-execution testing: immediately after rotation, they retain only 91 blocks, which is insufficient for the EVM's preceding-256-block `BLOCKHASH` window. Cached headers can temporarily conceal missing ancestry; once those headers are unavailable, execution results can differ from a full-history node.

For custom settings, use a conservative minimum of at least 1,024 blocks under the current pruning formula:

```text
minimum retained blocks = retention blocks - segment blocks + 1
```

Retention must also be divisible by segment size. This safety recommendation is documented, not enforced by the current startup checks.

For accelerated snapshot-bootstrap tests, build the segmented snapshot with `--retention-blocks 1080 --segment-blocks 30` and use matching geometry in the receiving node. Increasing retention cannot restore ancestry omitted from an existing snapshot.

Changing the segment size of an existing recent-history database is unsupported. Select the geometry before creating the database or use the supported rebuild/bootstrap workflow.

These are separate one-shot commands. Run them from the repository root using a local binary that includes `snapshot archive` and `snapshot recovery-checkpoint`.

#### External Storage And Future Transaction Retrieval

The archive is uncompressed. Its immutable files can be copied to offline storage or uploaded to file/object storage while preserving their relative paths.

For external publication:

1. Copy all referenced segment files.
2. Copy the immutable archive manifest.
3. Publish archive `latest.json` last.
4. Verify the external files against their recorded sizes and checksums.

Retain files referenced by older manifests, including manifests pinned by recovery checkpoints.

A future server application can import the segment indexes into a local resolver:

```text
transaction hash
→ segment, block number, and transaction position
→ download and verify the required segment database
→ open MDBX locally
→ return the transaction and receipt
```

The application can cache complete segment databases and evict them when no longer needed. The archive manifest alone does not locate an arbitrary transaction hash; the transaction indexes supply that mapping.

Uploading, remote downloading, cache management, and archive-backed explorer or JSON-RPC endpoints are not implemented by these builder commands.

The archive does not preserve historical state tries or provide historical balances, historical contract calls, historical storage queries, complete address activity, or a complete historical log-search index.

#### Backup And Cutover Boundaries

The archive preserves transaction history. The linked checkpoint supplies current state and consensus data at C. Validator identities and configuration require separate backups.

Keep the original database until the archive, recovery checkpoint, and intended external copies have been verified. Before replacing the node database, ensure blocks produced after C remain recoverable from another trusted source, or stop production at C before cutover.

These commands do not activate checkpoints or delete source history automatically.

The source node may remain online during construction, but its database must not be deleted, replaced, or pruned during export. Recovery verification reads historical payloads through A and can be I/O intensive.

Checksums establish consistency under the trusted operator-controlled archive model; they do not independently authenticate an untrusted source.

<!-- START ALPHA CHANGE 2099 -- document the 128 MiB cumulative archive manifest limit -->
Each archive manifest describes the complete archive and has a 128 MiB size limit (134,217,728 bytes). This limit applies to the manifest JSON, not to the archive databases or transaction indexes. Builders and readers must support the same limit. Do not remove earlier entries to work around it.

The limit does not allocate 128 MiB upfront. Processing costs grow with the actual manifest size, and decoded metadata consumes additional memory.
<!-- FINISH ALPHA CHANGE 2099 -- document the 128 MiB cumulative archive manifest limit -->

<!-- START ALPHA CHANGE 1658 -- document separated genesis and recent-history segments -->
Recent mode stores block zero in a permanent genesis database and stores post-genesis blockchain history in independently removable, block-numbered MDBX segment directories. Each post-genesis segment contains the canonical headers, number-to-hash mappings, bodies, receipts, and transaction lookup records for its block range.


```text
chain-data/blockchain/
├── genesis/
│   ├── mdbx.dat
│   └── mdbx.lck
└── segments/

    │   ├── mdbx.dat
    │   └── mdbx.lck
    ├── segment-00000000000000001801-00000000000000003600/
    └── ...
```

At a 2 second block time:

```text
43200 blocks = about 24 hours of retained history
1800 blocks = about 1 hour per segment
```

Block zero is stored directly in `genesis/`; it is not wrapped in an artificial segment directory. When a completed post-genesis segment falls outside the configured retention window, the node closes it and removes its directory from `segments/`. This physically returns the segment's storage to the filesystem without compacting or rewriting the active MDBX segment.

The trie and consensus databases are separate from blockchain-history segments and are not deleted by segment retirement.

`INNBC_HISTORY_RETENTION_BLOCKS` must be at least as large as `INNBC_HISTORY_SEGMENT_BLOCKS` and must be exactly divisible by it.

Full and recent modes use different blockchain directory layouts. Changing an existing node between these modes requires rebuilding its blockchain data from genesis or from an appropriate snapshot. Changing the segment size of an existing recent-history database is also unsupported because persisted segment boundaries must match the configured geometry.

## Recent history node maintenance

This procedure rebuilds a recent-history node from a compact snapshot produced by the full-history node. It is intended for planned maintenance when the recent node's live trie database has grown and should be replaced with the current compact state.

This is not an online trie garbage collector. The recent node must be stopped while its local databases are reset. The full-history node and its snapshot source must remain available.

Use `INNBC_SNAPSHOT_BOOTSTRAP_REQUIRED=true` during this procedure. Strict bootstrap mode guarantees only two outcomes:

- The snapshot is discovered, staged, validated, activated, and the node starts successfully.
- Snapshot bootstrap fails or is skipped, and the node does not start.

Strict mode prevents a maintenance restart from silently falling back to the old local database or genesis synchronization.

This procedure is only valid for a node configured with:

```text
INNBC_HISTORY_MODE=recent
```

Do not perform this procedure on the full-history node.

## MDBX Page Size

Generated node environments use `INNBC_MDBX_PAGE_SIZE_BYTES=4096`. The corresponding CLI flag is `--mdbx-page-size-bytes`.

An absent setting or blank textual value selects 4096 bytes. Explicit supported values are 4096, 8192, 16384, 32768 and 65536. Invalid nonempty values fail validation.

Change this setting only when creating new compatible blockchain and trie databases. Existing database page sizes cannot be changed in place. Local databases and selected snapshots must match the configured size; mismatches stop startup rather than converting or replacing existing databases.

<!-- START ALPHA CHANGE 3505 -- explain explicit foreground pages and locked recovery validation -->
The packaged builder's destination setting is `INNBC_SNAPSHOT_BUILDER_MDBX_PAGE_SIZE_BYTES=4096`. Direct foreground commands do not automatically read node or builder environment files. The complete examples explicitly pass `--mdbx-page-size-bytes 4096`; pass another supported value when required by the destination policy or existing databases.

Source databases retain their existing geometry. Builders can read a 4096-byte source and construct an 8192-byte destination. Snapshot consumers must use matching page sizes. An in-place trie rebuild must match the retained blockchain database; use 8192 instead of the example's 4096 when that blockchain database uses 8192-byte pages.

Existing archives and reused recovery artifacts must match the selected destination policy. Recovery construction rechecks archive compatibility after acquiring both publication locks and before selecting the archive or creating checkpoint staging. A mismatch preserves existing publications and releases the locks.
<!-- FINISH ALPHA CHANGE 3505 -- explain explicit foreground pages and locked recovery validation -->

Consensus storage retains its separate fixed 4096-byte page size. `node info` can display the public page-size environment setting; it does not open or validate chain databases.

## MDBX Map Size

<!-- START ALPHA CHANGE 3081 -- document role-specific MDBX configuration and maintenance -->
The code default is 1024 GiB (1 TiB). Full-history environments use:

```ini
INNBC_MDBX_MAP_SIZE_GB=1024
# START ALPHA CHANGE 3505 -- document full-history database pages --
INNBC_MDBX_PAGE_SIZE_BYTES=4096
# FINISH ALPHA CHANGE 3505 -- document full-history database pages --
```

The blockchain database and trie database each receive that allowance independently.

Generated recent-history environments explicitly use:

```ini
INNBC_MDBX_MAP_SIZE_GB=128
# START ALPHA CHANGE 3505 -- document recent-history database pages --
INNBC_MDBX_PAGE_SIZE_BYTES=4096
# FINISH ALPHA CHANGE 3505 -- document recent-history database pages --
```

Recent storage divides the blockchain allowance across its retained segments, subject to the existing per-segment minimum. The permanent genesis database also receives the per-segment allowance. The recent node's trie independently receives the configured 128 GiB allowance.

Consensus uses its own 1 GiB MDBX allowance and is not configured by this variable.

The packaged snapshot builder separates its destination settings:

```ini
INNBC_SNAPSHOT_BUILDER_MDBX_MAP_SIZE_GB=1024
# START ALPHA CHANGE 3505 -- document builder destination pages --
INNBC_SNAPSHOT_BUILDER_MDBX_PAGE_SIZE_BYTES=4096
# FINISH ALPHA CHANGE 3505 -- document builder destination pages --
INNBC_SNAPSHOT_BUILDER_SEGMENTED_MDBX_MAP_SIZE_GB=128
```

| Builder operation | Destination setting |
| --- | --- |
| `segmented` | Explicit segmented setting: 128 GiB |
| `checkpoint` | General setting: 1024 GiB |
| `recovery-checkpoint` | General setting: 1024 GiB |
| `archive` | General setting: 1024 GiB per archive database |
| `backup` | General setting: 1024 GiB for the blockchain copy |

The segmented setting is required; a missing or empty value stops wrapper dispatch.

Direct CLI operations do not read the builder environment. Their shared default is 1024 GiB. Pass `--mdbx-map-size-gb 128` explicitly when building a segmented snapshot for the configured recent nodes.

These are database growth allowances, not upfront physical disk allocations. The source is opened read-only using its stored geometry; the selected destination setting governs newly constructed databases. Matching source and destination allowances is not required, but the copied data must fit the destination.

Recent blockchain segments are retired automatically. The trie is reclaimed through the documented maintenance workflow using a recent snapshot containing reachable checkpoint state; no live trie garbage collector is introduced.

The maintained generators and templates supply these settings. Regenerate `localtestclient` and `dist` outputs from the completed source instead of manually editing generated files.

```bash
sudo systemctl stop innbc-node@node1 innbc-node@node2 innbc-node@node3 innbc-node@node4 innbc-node@node5 innbc-node@node6

sudo innbc-chain node prepare 6 \
  --base-dir /var/lib/innbc \
  --config-dir /etc/innbc \
  --chain /etc/innbc/genesis.json \
  --mode private-local
```

Do not delete validator identity keys unless intentionally replacing node identities.

## Local Database Backups And Optional Trie Reconstruction

Run these commands from the repository root. Direct localtestclient commands
use explicit CLI options and compiled defaults. They do not automatically read
generated node env files or `/etc/innbc/snapshot-builder.env`.

Create a blockchain database backup from local full-history node1:

```bash
./localtestclient/bin/innbc-chain snapshot backup \
  --chain localtestclient/genesis.json \
  --data-dir localtestclient/nodes/node1 \
  --out localtestclient/database-backups \
  --mdbx-map-size-gb 1024 \
  --mdbx-page-size-bytes 4096 # START ALPHA CHANGE 3505 -- document backup destination storage geometry --
# FINISH ALPHA CHANGE 3505 -- document backup destination storage geometry --
```

Normal source-node operation may continue during export. Do not replace,
delete, prune or restore the source database while the backup runs.

The command prints the completed backup directory. It contains `backup.json`,
the preserved `genesis.json`, and `chain-data/blockchain/mdbx.dat`. It contains
no trie, consensus state, keys or startup snapshot pointers.

Preserve the completed archive unchanged. For optional trie reconstruction,
prepare a separate working copy at `localtestclient/backup-work`, then run:

```bash
./localtestclient/bin/innbc-chain node trie-rebuild \
  --chain localtestclient/backup-work/genesis.json \
  --data-dir localtestclient/backup-work \
  --mdbx-map-size-gb 1024 \
  --mdbx-page-size-bytes 4096 # START ALPHA CHANGE 3505 -- document trie reconstruction storage geometry --
# FINISH ALPHA CHANGE 3505 -- document trie reconstruction storage geometry --
```

Use the genesis preserved in the backup, including when reconstructing a
downloaded production backup. Do not substitute the local test network's genesis.

The working trie directory must be absent or empty. No node or maintenance
process may use the reconstruction target concurrently. Complete unified
history and the existing allocation-based genesis requirements apply.

Reconstruction is optional and can run locally or on the server. Local replay
is recommended when practical to avoid loading the production server.
Neither command downloads, uploads or schedules backups automatically.
